# Сверка требований OMNIA: журнал незавершённого аудита

**Статус: аудит начат, не завершён.** Цель — не потерять требования между исходным документом, последующими решениями пользователя, новым ТЗ и кодом. Наличие пункта в ТЗ не означает реализацию. Этот документ пока не является полным поэлементным покрытием и не доказывает, что ничего не упущено.

Позднейшие прямые решения пользователя в истории проекта: Direct без внешних `FSUSB30MUX`, `74HC125` и `AO3401` USB switch; весь realtime DSP на AT32; 44,1/48 кГц, 88,2/96 кГц — будущее после реализации и измерений, без forced upsampling; PB0/PB2/PB4/PB8; PCM5102A; VS1838B; ST7789 I80; BT отложен до фото; и прочие зафиксированные в новом ТЗ требования. Наличие решения нужно подтверждать конкретной записью, а не придумывать.

Если старое описание конфликтует с более поздним решением, сохраняется пользовательская цель и отмечается **какое** решение заменило **какую** реализацию. Не восстанавливать старые распиновки, DSP на ESP, SPI-интерфейс дисплея, внешние коммутаторы или неработающие примеры кода лишь потому, что они есть в архиве. Не удалять другие функции по умолчанию. Фактическую возможность и приоритет неопределённых целей отмечать отдельно.

## Порядок завершения аудита

1. Разобрать исходный документ по требованиям: функциональные возможности, точные параметры, сценарии отказа и интерфейсы; каждому требованию присвоить идентификатор и ссылку на источник.
2. Для каждого указать: «сохранено без изменения», «заменено поздним решением», «ещё не перенесено», «технически не подтверждено» или «требует решения». Отдельно отметить статус кода: не реализовано / частично / host-тест / проверено на железе.
3. Сверить требования из переписки и принятые изменения, включая сервисное управление усилителем, частоты, комплект плат и ограничения. Не восстанавливать устаревшие схемы из архива.
4. Связать каждый пункт с конкретным разделом ТЗ, исходниками/схемой и измеримым критерием приёмки. Только после полноразмерной проверки можно заявить о покрытии; неподтверждённые случаи остаются открытыми.
5. Сначала обеспечить безопасный независимый цифровой стенд, одновременно продолжая программную разработку. Публиковать изменения только в рабочую ветку после восстановления доступа и проверять реальный push/CI.
